# Changelog

All notable changes to the Portcullis core stack. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project
uses [semantic versioning](https://semver.org/) with `vMAJOR.MINOR.PATCH`
tags (integration contract §1). `release.yml` publishes the section of a
tag's version as its release notes.

## [Unreleased]

### Added
- **Signing in as someone else** (contract §4, §5, §8, §8.1 "Impersonation", §15.2; sign-in part 3; ships with portcullis-keycloak and the Hub of the same release — upgrade all three together): Keycloak starts with `--features-disabled=impersonation` (its own impersonation answers "feature disabled") and gets `PORTCULLIS_PORTAL_URL`; `realm-export.json` adds the `portcullis-impersonation-notice` required action and `IMPERSONATE` to the events types; `./portcullis keycloak configure` adds the extension's `impersonation` mapper to the `acr` scope (next to `amr`) and registers / enables the notice action; `X-Forwarded-Impersonator` / `X-Forwarded-Impersonation` are in all four forward-auth middlewares' `authResponseHeaders` (client copies deleted); group-gate reads the Hub's `impersonation.json` (`GATE_IMPERSONATION_FILE`); the Hub gets `HUB_IMPERSONATION_MAX_MINUTES` from `IMPERSONATION_MAX_MINUTES` (1–30, default 30); mcp-gate refuses every token with an `act` or `pc_imp` claim (403 `impersonated`, "a session as someone else can't use AI tools").

- **A second issuing CA for browser certificates, `pki_file`** (contract §8.1 "Internal certificate authority", sign-in part 2): `./portcullis pki setup` adds `pki_file` (CN `<domain> Browser Certificate CA`, 5 years, signed by the existing root; CRL auto-rebuild + delta CRLs like `pki_int`) and its `browser-cert` role (client certificates only, CN never from the CSR, `max_ttl=$CLIENT_CERT_TTL`, rewritten every run), also next to an existing `pki_int`. It exports `certs/yubikey-ca.crt`, `certs/browser-ca.crt`, `certs/ca-chain.crt` = root + `pki_int` + `pki_file` (Traefik's `protected-any` / `authaware`), `certs/ca-chain-yubikey.crt` = the `pki_int` certificate alone, no root (`protected`) and the truststore's `portcullis-yubikey-ca.pem` / `portcullis-browser-ca.pem`; whenever `pki_file` is created or a chain on disk is out of date it rewrites both chains and the truststore, so the next `up` restarts Traefik and Keycloak. It refuses equal intermediate CNs; `--force` destroys both CAs. enroll's Vault policy adds `pki_file/sign/browser-cert`, list / read on `pki_file`, and revoke + `crl/rotate` on both mounts. `cert list` gains a KIND column (`YubiKey` / `Browser`), `cert revoke` finds the serial on `pki_int` then `pki_file` and rotates that CA's CRL (it no longer writes `certs/crl.pem`), `cert sync` writes the union of both CAs' revoked serials (either list failing leaves the file unchanged), and `cert enroll` names the Sign-in page (`https://people.<domain>/signin`) for renewals. Both roles refuse IP / URI / other SANs (`allow_ip_sans=false`, no allowed URI / other SANs) and enroll's policy denies `alt_names`, `ip_sans`, `uri_sans` and `other_sans` on both sign paths. `traefik/dynamic/tls.yml`: `protected` now trusts `/certs/ca-chain-yubikey.crt` only (a browser certificate never passes it), and the new `protected-any` option (`RequireAndVerifyClientCert`, `/certs/ca-chain.crt`) accepts either kind. Vault answers are read strictly: the CLI exits 2 for every API error, so only Vault's own "No value found" counts as empty — a sealed Vault or a 403 never empties the revoked list, never sends `cert revoke` to the other CA and never wipes or re-creates a CA; `pki setup` also refuses to re-create `pki_file` while `certs/browser-ca.crt` exists (restore, or `--force`).
- **`./portcullis signin reset-core`** (contract §8.1 "Lockout guard and signin reset-core"): the recovery when no administrator can sign in to the Hub. It stops the Hub, runs `hub signin reset-core` in a one-off container of the Hub's image as its user (uid 10001) — `hub` and `people` back on the built-in Standard template, Standard restored and enabled with its methods switched on, audited `signin.reset_core` by `cli` — and starts the Hub again, also when the stop or the reset failed or you interrupt it (the one-off container is never a Traefik target). Asks you to type `reset`; `--yes` for scripts (required without a terminal).
- **enroll `GET /internal/certificates`** (contract §9.4) on the Hub's invite listener (`enroll:8444`, the same bearer; `401` otherwise): the YubiKey (`pki_int`, role `client-cert`) client certificates issued, `{"certificates": [{"user", "serial", "not_after", "revoked"}]}`, read from Vault with each certificate's revocation state. Anything Vault can't answer within 15 s — a serial, a certificate or its revocation state — is a `503` for the whole list (the Hub then treats certificates as unknown), never a guessed `revoked: false`. No private material or PEM in the answer.
- **Keycloak is Portcullis's own image with the sign-in extension** (contract §1, §8.1; ships with portcullis-keycloak and the Hub of the sign-in release — upgrade all three together): the `keycloak` service runs `${KEYCLOAK_IMAGE:-ghcr.io/porelli/portcullis-keycloak:edge}` (the official Keycloak pinned by digest plus the extension) and mounts `hub_data` read-only to read the Hub's `signin-keycloak.json` — missing or invalid means nobody signs in. The realm's browser flow `portcullis-universal` signs in with the extension's methods (YubiKey certificate, the three passkey kinds, a password while the method is on — never for `admin` / `portcullis-hub`) and ends with the client's sign-in template; no Level-of-Authentication conditions or map are left (`acr.loa.map` `{}`), every method stays in the amr for 10 h, `portcullis-forward-auth` has no default acr. A setup link's session gets amr `inv` (no method; the person touches the new passkey once more to open apps), and the post-broker flow ends with the template check. Brute-force protection: 10 failures, then 60 s more per failure up to 15 min, never permanent. Passkey registration asks for direct attestation with any attachment (the extension decides the kind) and passes the extension's WebAuthn hints (`webauthn-register.ftl` / `webauthnRegister.js` in the `portcullis` theme); the stock two-factor `webauthn-register` action is disabled. `./portcullis keycloak configure` rebuilds the changed flows and asserts all of it; `version` and backups' `MANIFEST.json` name the Keycloak image; `upgrade` warns about a pinned `KEYCLOAK_IMAGE`; `release.yml` requires a released, digest-pinned `KEYCLOAK_IMAGE` default. CI builds the image from a same-named portcullis-keycloak branch (`.github/actions/keycloak-image`), else pulls `edge`.
- **MCP gate, first part** (`mcp-gate/`, contract §15.1–§15.4): a Go service that reads the Hub's `mcp-gate.json` / `mcp-credentials.json` strictly (a refused or unreadable file refuses every request, a missing one means AI support is off), decrypts per-person app credentials with its own age key, checks Keycloak access tokens for exactly the requested resource (signature RS256/ES256 via a throttled JWKS, issuer, `typ`, times ±60 s, authorized client, audience, scope, LoA, population and expiry, `Origin`) and serves RFC 9728 metadata per resource. CI runs its unit tests (`go vet`, gofmt, `go test -race`); Dependabot tracks `mcp-gate/go.mod`.
- **MCP gate, per-app bridge** (`mcp-gate/internal/bridge`, contract §15.5): an allowed request for a companion is served by an MCP server of the person's own (sessions bound to person and resource; the gate's session ids, never the upstream's) that forwards tools, resources and prompts to the companion through an MCP client of the gate, speaking the newest version both support. The upstream gets only the identity the template declares (`app_token` credential, `token …` or HTTP Basic; or `identity_headers` with the caller secret) plus the MCP transport headers — nothing the client sent, no cookies either way; app_token people without a credential wait for one (single flight per person) and are never sent anonymously. Tool policy: `never` / read-only `writes` hidden and refused (case-folded globs, `tool:method` on the arguments, ambiguous arguments refused), `confirm` and destructive-annotated tools need a confirmation (refused until confirmations exist), sampling and roots declined, URL elicitations only to the app's own hosts and `people.<domain>`. Sessions of people leaving a population are closed at the next file change. Results are bounded (16 MiB) and timed out (120 s).
- **MCP gate, limits, access log and Hub API** (`mcp-gate`, contract §15.6–§15.9): per-person rate limits (120 requests/min per app with a burst of 30, 60 tool calls/min per app, 600 requests/min overall, 10 confirmations/hour, 10 credential mints/min; over a limit `429` with `Retry-After`). Every MCP request is one line in `mcp_gate_data/access.jsonl` (0640, group 10001, kept 90 days): person, AI client, app, method, tool, a SHA-256 of the canonical arguments and the decision — never arguments, results, tokens or credentials. While the log can't be written for more than 30 s, tool calls are refused (`503` "AI activity can't be logged right now"). The gate asks the Hub to mint a missing app credential and to create and consume confirmations (link to `people.<domain>/confirm/<id>`); if the Hub can't be reached or answers anything unexpected, the call is refused and the app never called.
- **MCP gate, confirmations at the gate** (`mcp-gate`, contract §15.6): a tool that needs the person's approval is forwarded only after the Hub consumed a matching approved confirmation (person, app, tool and SHA-256 of the canonical arguments; single use; changed arguments need a new one). The person's AI client is told to open `people.<domain>/confirm/<id>`: an `input_required` result with a URL-mode elicitation for 2026-07-28 clients that declared URL elicitation, an `elicitation/create` request for 2025-11-25 ones, otherwise the text with the link. Declining or dismissing it does nothing; never form mode, never `401`/`403`.
- **MCP gate, "All my apps" and the Portcullis MCP** (`mcp-gate`, contract §15.9–§15.10): `mcp.<domain>/mcp` (scope `mcp:all`) gives a person, on one connection, the tools, resources and prompts of every app they can use through AI (named `<instance>__<tool>`, descriptions prefixed `[<label> · <host>] `) and their Portcullis tools (`portcullis__<tool>`; never the admin tools, never `invite_person` / `update_person` / `delete_person`). Each call goes to its app with the person's own identity and that app's own rules: population and expiry, sign-in strength, tool policy, confirmations, limits and one access-log line naming the app (`via: aggregate`). Lists are fetched from at most 4 apps at once within 30 s, cached 60 s per person and dropped at once when the person leaves an app (clients that listen get `notifications/tools/list_changed`); an app that doesn't answer is left out with "<label> is unavailable right now". Colliding names are both dropped. `hub.<domain>/mcp` (admins, `mcp:portcullis.admin`) and `people.<domain>/mcp` (`mcp:portcullis.people`) go to the Hub's `/mcp/admin` and `/mcp/people` through the same checks, limits and access log, with only the gate's own identity headers. Access-log lines of a call that used a confirmation carry its `confirmation_id`.
- **MCP gate in the core stack** (`mcp-gate` service, contract §15, §5, §8): built locally from `mcp-gate/Dockerfile` (pinned golang / alpine, uid 10005, `HEALTHCHECK mcp-gate healthcheck`), read-only, group 10001 only, on its own internal network `portcullis-mcp` (only the gate, Keycloak and the Hub; subnet `PORTCULLIS_MCP_SUBNET`, default `172.31.253.0/28`, range `172.31.253.8/29`; Keycloak pinned at `172.31.253.2`, the Hub at `172.31.253.3`, and the gate maps both names to them in `/etc/hosts`, never DNS) and on `portcullis-proxy` at the fixed `PORTCULLIS_MCP_GATE_IP` (default `172.31.250.3`; `./portcullis` refuses an address in the dynamic range, outside the subnet or equal to Traefik's; also shared with the Hub in `core.env`). `./portcullis init` / `up` generate `secrets/mcp-gate/` (the gate's age key — made offline by the image — and its recipient for the Hub, plus a 48-character secret shared with the Hub's new `:8890` listener; never printed). Traefik routes `mcp.<domain>` and the exact paths `/mcp` and `/.well-known/oauth-protected-resource/mcp` of `hub.<domain>` / `people.<domain>` to the gate, with no forward-auth (MCP clients send bearer tokens; browser routes keep oauth2-proxy, which accepts none); `mcp=*` in the group-gate map makes `mcp.<domain>` a core host. The access log volume `mcp_gate_data` is read-only in the Hub and part of the backups. CI checks the wiring, starts the gate, and drives every MCP route through Traefik. `./portcullis up` / `upgrade` / `init` / `restore` now refuse to run, and `status` fails, while a non-core container on `portcullis-proxy` answers to a core service name (`keycloak`, `hub`, `vault`, …). The enroll, domains and mcp-gate images share one pinned Go builder; the domains service refuses `mcp.<domain>` (a core host).
- **AI end-to-end tests** (CI job `e2e-ai`, contract §15): the whole stack with the Hub and the templates repo's Gitea (two instances), an MCP client on the official Go SDK (`tests/e2e/mcpclient`: RFC 9728 discovery, Keycloak authorization code with PKCE and `resource` for `portcullis-ai-claude-code`, loopback callback on `127.0.0.1:33418`) and `tests/e2e/e2e_ai.py` (Playwright sign-in and consent): a person sees only their own Gitea repositories through the gate, is refused (`403`) as soon as they leave the app and their minted Gitea token is deleted, a token works only at its own resource (`401` elsewhere, also a token for two resources), and an MCP token never opens an app page nor a browser cookie an MCP route; an administrator's destructive action through the Portcullis MCP needs a browser confirmation with a fresh passkey touch, works once and is audited as made through AI; "all my apps" lists exactly the apps a person can use (Gitea and Grafana, whose companion acts as the person through its trust network) and no admin tool; with AI support off every MCP endpoint answers 503; an app tool that needs a confirmation is confirmed on people.<domain> by the person alone, runs once with exactly the confirmed arguments and is logged with the confirmation; MCP clients that support URL elicitation get the confirmation link as one.
- **Keycloak: offline sessions for AI connections** (AI support, contract §8): the realm allows offline sessions of up to 30 days idle and 90 days in total (the Hub sets shorter values on its AI clients); refresh-token rotation stays off and is pinned (`revokeRefreshToken: false`): Keycloak has no per-client switch, and realm-wide rotation signs forward-auth users out when two requests refresh one session at once. `./portcullis keycloak configure` applies both to existing realms and never touches the Hub's `portcullis-ai` clients or `mcp:*` scopes. The browser e2e checks a forward-auth session through two refreshes with concurrent requests.
- **Domains service** (`domains`, contract §12): Hub admins enroll extra domains or subdomains with a DNS provider token (Cloudflare, Porkbun, Route 53, DigitalOcean, Hetzner — libdns). The service sets `<d>` / `*.<d>` A (and AAAA) records, obtains and renews a wildcard certificate per domain with ACME DNS-01 (lego), and hands the certificates to Traefik's HTTP provider over mutual TLS on the internal network `portcullis-certs` (only `tls.certificates`, every SAN checked before serving; no shared volume, no sidecar). Tokens are stored only age-encrypted in `domains_data` (key `secrets/domains/age.key`) and never logged or returned. `./portcullis init` / `up` generate `secrets/domains/` (API secret shared with the Hub, age key, the endpoint's private CA and certificates — renewed when < 30 days are left, then traefik and domains restart), detect the public IPv4 / IPv6 (`PORTCULLIS_PUBLIC_IPV4` / `_IPV6` override), and `status` warns about expiring endpoint certificates; backups include `domains_data` (encrypted). CI runs the service against Pebble with a fake DNS provider and checks the Traefik side.

### Changed

- **`enroll.<domain>` serves only setup links; the browser-certificate flow, both CAs' CRLs, group-gate's data and CA files, Keycloak events kept a year** (contract §4, §5 "Core routers", §8.1, §8.2, sign-in part 2; ships with the Hub and Keycloak image of sign-in part 2 — upgrade together): the `enroll` and `enroll-self` routers and the self-service forward-auth middleware are gone, `enroll-invite` (`PathPrefix(/invite/)`) is the only router on `enroll.<domain>` (anything else is Traefik's 404) and `group-gate-map.conf` has no `enroll` entry. The `people` router passes the presented certificate (`client-cert-pem@file`) for the YubiKey renewal on the Sign-in page. group-gate runs with group 10001, mounts `certs/yubikey-ca.crt` / `certs/browser-ca.crt` read-only (`GATE_YUBIKEY_CA_FILE` / `GATE_BROWSER_CA_FILE`) and writes its opened log to the new `group_gate_data` volume (`GATE_OPENED_DIR=/data/opened`; `10003:10001`, created by `./portcullis up`, backed up), which the Hub mounts read-write at `/group-gate-data` (`HUB_GROUP_GATE_DATA_DIR`) for sign-in history; the Hub also gets `HUB_CLIENT_CERT_TTL` (= `CLIENT_CERT_TTL`) and `HUB_CERT_EXPIRY_WARN_DAYS` (= `CERT_EXPIRY_WARN_DAYS`), Keycloak `PORTCULLIS_SIGNIN_URL` (`https://people.<domain>/signin`). `./portcullis up` creates the two CA files empty before the first `pki setup`; `up` / `upgrade` restart Traefik, Keycloak and group-gate whenever the CA, chain or truststore files differ from the stamp `certs/.pki-files.loaded` they were started with (written only after a successful restart). **Security:** `certs/ca-chain-yubikey.crt` (Traefik's `protected` option) now holds the YubiKey CA alone, without the root — Go's TLS server trusts every certificate in `caFiles` as an anchor and builds paths through the intermediates the client sends, so with the root there a browser certificate (whose `.p12` sends `pki_file` + the root) passed `protected` and reached `auth.method: mtls` apps; `tests/test_shell_libs.sh` checks the rule with `openssl verify -partial_chain`. The realm's `portcullis-signin` holds a second `portcullis-x509` execution (`x509-browser-config`: `browser_cert`, amr `file`, the browser CA, `pki_file`'s CRLs; `x509-config` gains `portcullis.method` `yubikey_cert` and the YubiKey CA) and keeps `LOGIN` / `LOGIN_ERROR` events for 365 days; `keycloak configure` pushes each x509 config onto the execution with that alias (another alias is left alone) and never touches the events config. `tls.yml`'s header says which of the four options uses which chain. `./portcullis status` and its textfile cover both kinds (label `kind`) and the browser certificate CA; status, the alerts, `.env.example`, README and the docs pointer say "YubiKey certificate" / "browser certificate" and point at the Sign-in page instead of the retired enroll pages.
- **group-gate: YubiKey and browser certificates told apart by issuer; both CAs' CRLs; the Sign-in page reachable with any method; the opened log** (contract §4, §5, §10, sign-in part 2; ships with the Hub and Keycloak image of sign-in part 2 — upgrade together): group-gate parses the presented leaf itself from `X-Forwarded-Tls-Client-Cert` (`client-headers@file` now passes it, `pem: true`; the Info text, whose Subject / Issuer Traefik doesn't escape, never decides anything) and counts it as `yubikey_cert` (amr `mtls`) only when `GATE_YUBIKEY_CA_FILE` (`pki_int`) is its issuer and verifies its signature, and as `browser_cert` (amr `file`) only for `GATE_BROWSER_CA_FILE` (`pki_file`); its one CN must match the LLDAP username grammar and equal the user exactly, and it must be within its validity. Equal CA subjects, a missing / unreadable / non-CA file, no CRL list configured, a list never read, or one more than an hour past its nextUpdate means no certificate counts. Revocation reads `GATE_CRL_URLS` and `GATE_DELTA_CRL_URLS` (space-separated; group-gate refuses to start while the old `GATE_CRL_URL` / `GATE_DELTA_CRL_URL` is set) and enforces the union of every list and the serial file on every host. Once every list has first been read, a CA file none of whose full or delta lists that CA issued (say `GATE_CRL_URLS` names `pki_int` only) is logged as a start-up WARNING: its certificates still count, revoked only through the lists and serial file that remain. On `people.<domain>` the Sign-in page's exact paths (`/signin`, `/api/me/signin`, `/api/me/signin/*`, `/static/*`: every normalised reading of the raw path inside the set, no encoded `/` or `\`) take "any switched-on method" instead of the `people` template. The present-certificate page covers both kinds, a step-up never asks for a certificate method whose amr the session holds, and the needs-stronger page's "Set up …" / "Sign-in methods" links and the portal's "Sign-in methods" link go to `https://people.<domain>/signin` (the portal's enroll links and "My passkeys" are gone). `/authenticated` is gone and `enroll.<domain>` is no longer a gated core host (still reserved). The first allowed request per (session, host) appends a line to `GATE_OPENED_DIR/<YYYY-MM-DD>.jsonl` (default `/data/opened`; directory 2770 group 10001, files 0640, a day file at most 8 MiB; written by one background thread from a bounded queue, so a hung volume never holds a request; never a token; a failed write is counted in `group_gate_opened_log_failures_total` and logged at most once a minute, never a deny), which the Hub's sign-in history reads. mcp-gate keeps the Hub's three help-to-reset tools (`person_sign_in`, `revoke_person_certificate`, `remove_passkeys`) out of "All my apps"; the shared sign-in vectors are re-copied from the Hub.
- **Static TLS options; `MTLS_ENABLED` is gone** (contract §5 "TLS tier per host"; ships with the Hub of the sign-in release — upgrade both together): `traefik/dynamic/tls.yml` is tracked and static with exactly `protected` (client certificate required), `authaware` (optional, verified if presented) and `public` (none requested). The Hub picks one per app from the app's sign-in template and the certificate methods switched on; core routers stay on `authaware`. `./portcullis config apply` handles only `ACME_STAGING` and never writes `tls.yml`; `init` no longer writes `MTLS_ENABLED` (a leftover line in `.env` is ignored).
- **mcp-gate reads gate file version 2 only: sign-in rules instead of LoA** (contract §8.1, §15.2, §15.4; ships with the Hub of the sign-in release — upgrade both together): each resource carries its compiled sign-in `rule` (the instance's template for an app, the `people` core template for `people.<domain>/mcp`, the `hub` one for `hub.<domain>/mcp` and `mcp.<domain>/mcp`) and the file lists the switched-on `methods`; `acr_loa` and `min_loa` are gone. A token meets a rule with its `amr` mapped through the method table, switched-on methods only — never a YubiKey or browser certificate (MCP clients present none), never a setup link (`inv`) or an unknown value; an unmet rule is `403` (`deny:sign_in`, "<label> needs a stronger sign-in than this connection has"), for "All my apps" per app (an app whose rule the token doesn't meet is left out, its calls refused). Version 1 files, `acr_loa` / `min_loa` keys, a rule outside the readers' limits (a group at the top, 1–8 items per group, depth ≤ 4, ≤ 48 methods) or naming a method that is off, and an app whose rule needs a certificate on every alternative refuse the whole file (`503`). The gate's shared vectors (`internal/config/testdata/`, `internal/signin/testdata/signin_vectors.json`) are byte copies of the Hub's (CI compares).
- **group-gate serves policy file version 6 only: sign-in templates** (contract §4, §5, §8.1; ships with the Hub and portcullis-keycloak of the sign-in release — upgrade all three together): each host's access rule is a compiled sign-in template (`core[host]` for core pages, else `hosts[host]`, else `default`) over the switched-on methods (`methods`), met by the session's `amr` through the method table; a YubiKey certificate counts only with the mTLS binding on the request. An unmet template answers `403` with a page, never a redirect: present your YubiKey certificate, a step-up that asks for one method (`/oauth2/start?pc_method=<method>`, also in `X-Stepup-URL`), or "needs a stronger sign-in" (the Keycloak extension's wording). v5 and older files, a missing file, an unknown key, a malformed rule or an unknown template reference deny every request. The Keycloak admin console's router (`auth.<domain>`) uses the Hub's core template. The membership checks (groups, path groups, the deny group, `expiring`) run first, so someone outside an app's groups gets the plain 403. The request metric's `result` is `stepup`, `needs_stronger` or `present_certificate` for the three pages. The portal checks its own core template. The session's methods are read from `X-Forwarded-Access-Token` only. oauth2-proxy's `loginURLParameters` drop `acr_values` and allow `pc_method` with the six method ids and `passkey`. `tests/signin_vectors.json` is a byte copy of the Hub's shared rule vectors (CI compares).
- **mcp-gate hardening (final review)**: a Keycloak signing key removed from the realm stops verifying within about 11 minutes (the key set is re-fetched once it is 10 minutes old and replaced by what Keycloak publishes; an unreachable Keycloak keeps the last set). A tool call is forwarded only once its access-log line has a reserved place, so an admitted call can never lose its line; tool calls are refused (`503`) as soon as the log writer fails or is stuck, not only after 30 s. One person can have at most 6 requests with a body in flight (`429` beyond), and request bodies in flight share a 512 MiB budget (`503` "the gate is busy" when spent); the gate's memory limit is now 1 GiB. `./portcullis up` / `upgrade` / `init` / `restore` refuse, and `status` fails, while a container on `portcullis-proxy` answers to an AI companion name (`portcullis-mcp-<instance>--<companion>`) without being that instance's single companion container. `status` shows when mcp-gate refuses every AI request (for example after `secrets/mcp-gate/age.key` was lost: the stored AI credentials can't be decrypted and the Hub doesn't re-key them — restore the key, or switch each app_token companion off and on), and a regenerated key warns about it.
- **Keycloak links LDAP users by LLDAP's `entryUUID`, not the username** (contract §8, hardening): the LDAP federation's `uuidLDAPAttribute` is `entryUUID` in `realm-export.json` and pushed onto existing realms by `keycloak configure` (`_kc_ldap_patch`). An account deleted and re-created under the same name in LLDAP is a new identity: Keycloak removes the old copy (its passkeys, sessions, consents, grants) and imports the new one with a new user id (`sub`); before, the new person inherited all of it. **Existing deployments:** after the upgrade every LDAP user's Keycloak copy fails validation at its next lookup (a sign-in or the Hub's 15-minute listing) and is replaced by a new one — new Keycloak ids, passkeys gone: re-invite everyone (`./portcullis invite admin` for the bootstrap admin), and native-OIDC apps see a new `sub` per person. CI: the "deleted in LLDAP leave Keycloak" step re-creates a name and compares Keycloak ids; restore keeps the admin's id and link.
- **group-gate reads `user-attributes.json` version 2 only** (contract §4.1, template contract v3; ships with the Hub release that writes v2 — upgrade both together): version 1 gives no attribute headers (never a deny). The new `hosts` section adds per-host headers (`hosts.<host>.<Header-Name>.<user>`), returned on allow for that host only: one value, control characters stripped, over 1 KB dropped, no `,` encoding; a header a host declares replaces the same-named field header on that host for every user. Host keys that aren't lowercase valid hostnames and invalid header names are skipped (logged).

  headers are trusted only from Traefik's fixed address on `portcullis-auth`.
- **group-gate public guard** (`/public-guard`, middleware
  `portcullis-public-guard@docker`) for the Hub's public exceptions: allows
  only the paths a subdomain publishes in the policy file's `public_paths`
  and refuses requests carrying `Authorization`, `Proxy-Authorization` or
  the app's credential headers, cookies or query parameters (names
  normalised the way PHP's `php_register_variable_ex` does). Policy file
  version 3; the guard requires exactly 3, and the Hub and core must be
  upgraded together.
- **group-gate**: `path_groups`, policy file v3 (v1–v3 accepted, parsed file
  cached on inode/mtime/size), reserved deny group,
  `/authenticated` (self-service routes), `/healthz`, `/metrics`.
- `portcullis version` (core version and the Hub image in use).
- **Releases**: `release.yml` for `vX.Y.Z` tags (full CI, released + pinned
  Hub image required, notes, tarball + sha256). This changelog.
- **Supply chain**: Dependabot (compose, enroll Dockerfile and Go modules,
  actions, e2e pip); CI fails on any image not pinned `tag@sha256` or any
  action not pinned by commit SHA.
- **Tests**: CLI and shell-library tests, group-gate unit tests, enroll Go
  tests, Playwright e2e login (passwords, passkeys, step-up, X.509, mTLS
  binding, revocation), backup → off-host → restore into a fresh stack,
  monitoring checks, promtool rule tests.

### Changed

- **Identity is the LLDAP username, never the email** (users can edit their
  own email in LLDAP): `X-Forwarded-User` / `X-Auth-Request-User` /
  `X-Auth-Request-Preferred-Username` carry the username (oauth2-proxy
  injects the `preferred_username` claim; its session user is Keycloak's
  `sub`), the email moves to `X-Forwarded-Email`; Keycloak does not mark
  LLDAP email as verified. group-gate takes the user only from
  `X-Auth-Request-Preferred-Username` and denies requests without it.
  Header-auth apps must log users in by username.
  `keycloak configure` maintains an `email-unverified` client scope (`email`
  claim, no `email_verified`) for apps that refuse `email_verified=false`
  (Hub templates opt in with `email_verified_claim: false`).
- **Step-up** goes to `https://auth.<domain>/oauth2/start?acr_values=…&rd=<app>`;
  oauth2-proxy is routed on `auth.<domain>` only (a host-less `/oauth2/`
  router gets Traefik's 421 on tiered hosts).
- **Delta CRLs** on pki_int (`enable_delta`, rebuilt every minute):
  `auto_rebuild` defers full CRL rebuilds, so revocations made in Vault
  directly are only in the delta CRL until then; group-gate
  (`GATE_DELTA_CRL_URL`) and Keycloak's X.509 login read both.
- **Docker socket**: only two socket proxies mount it (Traefik read-only, the
  Hub what `docker compose` needs), each on its own internal network.
- **Hardening**: every core image pinned by digest; `no-new-privileges`,
  `cap_drop: ALL`, memory/pid limits on every service; read-only root
  filesystems and non-root users wherever the image allows (exceptions in
  `docs/hardening.md`). Keycloak runs `start` (production mode).
- The Hub gets a generated env subset (`secrets/hub/core.env`), the proxy
  secret via a Traefik middleware, and no LLDAP credentials.
- `portcullis-proxy` has fixed IPAM with Traefik at `PORTCULLIS_TRAEFIK_IP`,
  the only peer header-auth apps trust.
- One base domain per installation (`PORTCULLIS_DOMAIN`), enforced by
  group-gate and the Hub.

### Removed

- `scripts/*.sh` (replaced by `./portcullis`), Vault dev mode and its static
  token, public default secrets, the unused Traefik static configuration
  files (Traefik is configured through environment variables).
